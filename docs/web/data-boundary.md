# Local content boundary

Implemented in Web 01; public launch and protected access remain unavailable. This document narrows the current executable scope of the [data requirements](../../plan/data-and-publication.md) and the unmerged [Web00 contract specification](https://github.com/DangHoangGeo/giaoxuthachbi-simulator/blob/84edc9e/docs/web/contracts.md).

## Public reads

`web/src/lib/server/public-content.ts` imports `server-only` and exactly two local inputs: `web/content/current.json` and `web/content/release.json`. They currently contain an unpublished pointer and `null`. No input path comes from a URL/user, no external store is connected, and no actual church records or images are copied. The home route fails with a generic error if these inputs are invalid; it keeps the unpublished shell for the present valid empty state. Content presentation is phase 02/03 work.

The recursive strict Zod schemas reject unknown fields, including nested private paths. Public release IDs, source revisions and review references must be opaque IDs rather than private filenames or staff records. Syntax is enforced; semantic privacy still requires editorial review. Text stays plain text for escaped React rendering; it is not trusted HTML. Both languages are required. Asset paths are hash-named local derivatives only, with bounded declared dimensions/bytes and matching path/checksum. Phase 02 adds a maintainer derivative exporter and mandatory build-time byte/metadata/inventory checks, described in the [media workflow](public-content.md#private-media-preparation). Rights/privacy remain human reviews; a `cleared` field does not prove permission by itself.

Dates retain explicit month/day precision; impossible days and unzoned instants reject. Unknown occurrence stays `null`, separate from a reported-as-of day. The validator does not infer a completion day from a report day. Verification needs an evidence reference. Corrections require a notice and coherent timestamps; IDs are unique across the release, slugs are unique within their page/event collections, event media references resolve, and an ID listed as retired cannot be live in that release. Other references are opaque labels whose supporting records require maintainer review. Checking retirement/corrections against earlier releases and detecting unsupported increases in date precision remain publication-history checks for phase 03. A schema cannot establish whether an editorial statement is true.

The pointer pins one exact `releaseId` and SHA-256. Hash input is the parsed strict release represented as UTF-8 JSON, with recursively sorted object keys (JavaScript code-unit ordering), arrays in supplied order, JSON primitive serialization and no insignificant whitespace. This defined project algorithm is not a claim of RFC 8785 implementation. Changing a field invalidates the pointer; key insertion order does not. Synthetic fixtures are schema examples with `fixtureOnly: true`; the production reader always rejects them. The tests exercise the production shape only in memory with fictitious data. Nothing publishes them.

Unknown fields, invalid pointers, mismatched release/hash and fixtures yield only `{state: "unavailable"}`; validation details/private values are not returned or logged. The intended repository publication method will leave the previous deployed artifact active when a new build fails (no deployment exists yet); switching a remote pointer, retaining last-known client data and rollback/removal are not yet implemented. No endpoint or browser cache for releases is added here.

## Protected reads and build inspection

`web/src/lib/server/protected-content.ts` has a separate server-only interface which **always denies access**, including caller-supplied administrator/site-manager claims. It has no storage reader, provider or credentials. Review/site/sign-in URLs still return 404. This is deliberate absence of access, not completed authentication. Phase 05 must implement trusted server sessions, permission checks at every read, cache isolation, revocation and private delivery before use. Detailed protected engineering/geometry schemas are still pending their later consumers; public validation cannot approve an engineering release.

After a production build, run `npm run check:boundary` from `web/`. It scans static, server and standalone output for synthetic private canaries and source-directory markers, resolves output-file traces and rejects references escaping `web/`. It prints labels/relative artifact names, not canary contents. This is bounded leakage evidence, not a universal secret scanner or a substitute for access-control tests. CI must repeat it on each build; test fixtures themselves must never be imported by application code.
