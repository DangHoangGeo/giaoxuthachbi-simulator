# Local content boundary

The public boundary was implemented in Web 01; the phase-05 shared-password architectural preview adds the separate private read path described below. Full engineering access and release acceptance remain open. This document narrows the current executable scope of the [data requirements](../../plan/data-and-publication.md) and the unmerged [Web00 contract specification](https://github.com/DangHoangGeo/giaoxuthachbi-simulator/blob/84edc9e/docs/web/contracts.md).

## Public reads

`web/src/lib/server/public-content.ts` imports `server-only` and exactly two local inputs: `web/content/current.json` and `web/content/release.json`. They now contain the owner-authorized `development-content-20261008-two` release: sixteen project concepts, two owner-reported events and a limited project introduction. See [permission and scope](publication-permission.md). No input path comes from a URL/user, the public reader does not use external storage, and only the selected public-safe derivatives and text enter public inputs. The home route fails with a generic error if these inputs are invalid; it keeps the unpublished shell for the present valid empty state. Phase 02 consumes approved narrative/media through this reader; phase 03 consumes reviewed event records through the same reader and exposes only allowlisted [version metadata](timeline.md) for freshness checks.

The recursive strict Zod schemas reject unknown fields, including nested private paths. Public release IDs, source revisions and review references must be opaque IDs rather than private filenames or staff records. Syntax is enforced; semantic privacy still requires editorial review. Text stays plain text for escaped React rendering; it is not trusted HTML. Both languages are required. Asset paths are hash-named local derivatives only, with bounded declared dimensions/bytes and matching path/checksum. Phase 02 adds a maintainer derivative exporter and mandatory build-time byte/metadata/inventory checks, described in the [media workflow](public-content.md#private-media-preparation). Rights/privacy remain human reviews; a `cleared` field does not prove permission by itself.

Dates retain explicit month/day precision; impossible days and unzoned instants reject. Unknown occurrence stays `null`, separate from a reported-as-of day. The validator does not infer a completion day from a report day. Media whose earliest possible capture/creation day follows the publication day in Asia/Ho_Chi_Minh reject; a capture month overlapping publication retains its uncertainty. At least one public narrative entry is required before accepting a release. Verification needs an evidence reference. Corrections require a notice and coherent timestamps; IDs are unique across the release, slugs are unique within their page/event collections, event media references resolve, and an ID listed as retired cannot be live in that release. Other references are opaque labels whose supporting records require maintainer review. Phase 03 adds explicit church timezone, nullable occurrence intervals and maintainer history checks for retirement, stable event tombstones, append-only corrections and new evidence references for date/evidence changes; see the [publishing runbook](progress-publishing.md). A schema cannot establish whether an editorial statement is true.

The pointer pins one exact `releaseId` and SHA-256. Hash input is the parsed strict release represented as UTF-8 JSON, with recursively sorted object keys (JavaScript code-unit ordering), arrays in supplied order, JSON primitive serialization and no insignificant whitespace. This defined project algorithm is not a claim of RFC 8785 implementation. Changing a field invalidates the pointer; key insertion order does not. Synthetic fixtures are schema examples with `fixtureOnly: true`; the production reader always rejects them. The tests exercise the production shape only in memory with fictitious data. Nothing publishes them.

Unknown fields, invalid pointers, mismatched release/hash and fixtures yield only `{state: "unavailable"}`; validation details/private values are not returned or logged. The intended repository publication method will leave the previous deployed artifact active when a new build fails (the GitHub-connected Vercel project is now confirmed); switching a remote pointer, retaining last-known client data and rollback/removal are not yet implemented. No endpoint or browser cache for releases is added here.

## Protected reads and build inspection

`web/src/lib/server/protected-content.ts` has a separate server-only interface which **always denies access**, including caller-supplied administrator/site-manager claims. It has no storage reader, provider or credentials. That engineering interface remains denied. The separate `server/review/` modules implement only the owner-requested shared-password architectural preview: `/vi/review` and `/en/review` challenge anonymous requests with 401, and protected page/model handlers check a fresh private-origin policy before reading. Site/sign-in remain 404; unfinished children under review require authentication before 404. The private model/manifest/policy are not public build inputs. See [access controls](access-control.md) for cache isolation, expiry, revocation and the explicit shared-access limitations. Detailed protected engineering/geometry schemas are still pending their later consumers; public validation cannot approve an engineering release.

After a production build, run `npm run check:boundary` from `web/`. It scans static, server and standalone output for synthetic private canaries and source-directory markers, resolves output-file traces and rejects references escaping `web/`. It prints labels/relative artifact names, not canary contents. This is bounded leakage evidence, not a universal secret scanner or a substitute for access-control tests. CI must repeat it on each build; test fixtures themselves must never be imported by application code.

The public visit separately reads the strict build-validated `web/content/visit.json` and its single hash-named compressed GLB. This contains only a reviewed architectural display derivative. See [viewer boundary and profile](viewer.md); the full sharing file, exporter mappings and source records stay outside `web/`. The release remains a development preview.
